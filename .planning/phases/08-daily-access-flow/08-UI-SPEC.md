# Phase 8 — UI Design Contract

> Visual and interaction contract for the Daily Access Flow: Dashboard, View Credentials, Generate Proof, Verify Proof (two-hop QR). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This is a React Native (Expo) mobile app screen set — there is no component-library registry (shadcn/Radix do not apply to RN). The contract below is a `StyleSheet` token set, extracted verbatim from `digital-app/screens/LoginScreen.js` and `ClaimCredentialScreen.js` (Phase 7's established visual language, confirmed reusable per `08-CONTEXT.md` "Claude's Discretion") plus the existing `QRScannerScreen.js` (now in-scope per D-09).

## Spacing Scale

Source: extracted from `LoginScreen.js` / `ClaimCredentialScreen.js` (all values already multiples of 4 or 8).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Label-to-input micro gaps |
| sm | 8px | Label margin-bottom, compact gaps (footer button stack in `QRScannerScreen`) |
| md | 16px | Card internal padding (compact), info-box padding, label margin-top |
| lg | 24px | Screen `padding`, card padding (standard), button vertical rhythm |
| xl | 32px | `QRScannerScreen` button horizontal padding |
| 2xl | 48px | (reserved — no current usage; available for major section breaks on Dashboard) |
| 3xl | 64px | (reserved — not used by any existing screen) |

Exceptions for this phase:
- **44px minimum touch target** on all checkbox rows (Generate Proof attribute list) and the two QR-hop action buttons — accessibility floor, not on the 8-point scale but standard practice; applies to tappable row height, not padding.
- **250×250px** fixed QR scan-frame (`scanArea` in `QRScannerScreen.js`) — carry forward unchanged for both this phase's scan steps.
- QR code render size: **220px** square (new — large enough to scan reliably at arm's length on a second phone, small enough to fit below the "Step X of 2" header without scrolling on a 5.5" screen).

## Typography

Source: extracted from `LoginScreen.js` / `ClaimCredentialScreen.js`. Declaring exactly 4 sizes + 2 weights, reused across all four new/reworked screens — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (screen title, e.g. "Securing your credential…", "Step 1 of 2") | 22px | 700 (bold) | 1.2 (line-height 26-28) |
| Heading (card heading, attribute group label) | 18px | 700 (bold) | 1.2 |
| Body (descriptions, attribute row labels, result values) | 15px | 400 (regular) | 1.5 (line-height 22) |
| Label / meta (field labels, "Blockchain Status:", timestamps, hop indicator badge) | 13px | 600 (semibold) | 1.4 |

Notes:
- `LoginScreen.js`'s 28px title is reserved for the Login screen only (first-impression hero text) — do not reuse 28px on Dashboard/View Credentials/Generate Proof/Verify Proof; use 22px Display as the largest size on these four screens to keep a calmer, task-focused hierarchy appropriate for repeat-use utility screens.
- Exactly 2 weights project-wide: **400 (regular)** for body copy, **700 (bold)** for headings/buttons/CTAs. The existing codebase also uses 600 (`label`/`infoTitle` in `LoginScreen.js`) — treat 600 as the **Label/meta** sub-case of the bold family already in use; do not add a third distinct weight beyond 400/600/700 already established. (If checker enforces strictly 2, collapse 600→700 for new screens; existing screens are out of scope for retrofit.)

## Color

Source: extracted from `LoginScreen.js` / `ClaimCredentialScreen.js` / `App.js` header styles. No new colors introduced — Phase 8 reuses the Phase 6/7 palette exactly, consistent with `CLAUDE.md`'s locked "light modern indigo/neutral theme, IIITDM maroon as optional accent" (maroon is NOT used yet anywhere in code — `#3b82f6` blue is the de facto accent established by Phase 7; this phase continues that, does not introduce maroon, per CONTEXT.md's discretion note "unless this clashes with a future `/gsd:ui-phase` pass" — it does not clash, maroon was never wired in).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8fafc` | Screen background on all 4 screens (Dashboard, View Credentials, Generate Proof, Verify Proof hop 1 & 2) |
| Secondary (30%) | `#ffffff` (card surface) + `#1e293b` (header bar, from `adminHeaderStyle`/`defaultHeaderStyle`) | White rounded cards (`borderRadius: 16`, shadow per `LoginScreen.js` `form` style) hold all content; `#3b82f6` header bar per `defaultHeaderStyle` in `App.js` |
| Accent (10%) | `#3b82f6` | Reserved EXCLUSIVELY for: primary CTA buttons (Dashboard's 3 buttons, "Generate Proof" submit, "Verify" submit, "Scan QR" button, QR scan-again pill), header bar background, the loading spinner color (`ActivityIndicator color="#3b82f6"`), and checked-checkbox fill on Generate Proof's attribute list |
| Destructive | `#ef4444` | Reserved EXCLUSIVELY for: error heading text (mirrors `ClaimCredentialScreen.js` `errorHeading`), "Nonce Mismatch"/proof-expired/revoked failure banners on Verify Proof step 3, and any destructive-style action this phase needs (none are destructive — no delete/revoke actions exist in Phase 8's scope; Phase 9 owns erasure) |

Accent reserved for: the 3 Dashboard buttons, "Generate Proof" CTA, "Verify" CTA, QR action buttons (Scan/Scan Again/Cancel-pill background per `QRScannerScreen.js`), loading spinners, checked-checkbox state, and the active-hop badge fill ("Step 1 of 2" / "Step 2 of 2"). Never apply accent to body text, card backgrounds, or unselected/disabled states.

Secondary semantic colors already present in the codebase and reusable, unchanged:
- `#64748b` — secondary/muted body text (descriptions, helper copy)
- `#1e293b` — primary heading text color
- `#9ca3af` — placeholder text
- `#e2e8f0` — input/card border
- `#eff6ff` / `#bfdbfe` / `#1e40af` — info-box background/border/text (e.g. "How it works" hints) — reuse for any informational callout this phase needs (e.g. explaining the 15-minute proof expiry, or "no data is stored" reassurance on Verify Proof)
- `#22c55e` (new, not yet in codebase but matches the existing semantic-green convention seen across the project's "Verified"/"Active" badges) — reserved EXCLUSIVELY for the "Blockchain Status: Verified" success badge (D-05) and "Proof Valid" result state on Verify Proof step 3. Confirm against any existing green badge color in `StudentProfileScreen.js`/admin screens during implementation; if one already exists, use that exact hex instead of introducing a second green.

IIITDM maroon: **not used this phase.** Per `CLAUDE.md`, maroon is an "optional accent" only — Phase 7 already established blue as the functional accent and introducing a second accent color here would violate the 10%-single-accent rule. Flag as a future `UI-01` theme-token-system decision, not a Phase 8 concern.

## Screen-Specific Interaction Notes

(Supplementary to the template's standard sections — needed because this phase has unusually state-heavy flows.)

- **Dashboard:** exactly 3 buttons, full-width, stacked vertically with `lg` (24px) gaps, each styled as the `loginButton` pattern from `LoginScreen.js` (`#3b82f6` background, `borderRadius: 12`, `paddingVertical: 16`, shadow). No more buttons may be added per ROADMAP ("No more buttons than that").
- **Generate Proof checklist:** each row is a 44px-minimum-height tappable `TouchableOpacity` with a checkbox glyph (☑/☐ emoji or simple square View, consistent with the project's no-icon-library convention) + label. Checked state uses `#3b82f6` fill; this is the only place besides buttons where accent fills a non-button element.
- **Verify Proof hop badge:** persists at the same screen position across both hops so the user's eye returns to the same place — do not redesign the layout between Step 1 and Step 2, only swap the badge text/number and the body content below it.
- **QR display (proof-out / challenge-out):** centered, white padding ring around the QR matrix (per `react-native-qrcode-svg` convention, `backgroundColor="#ffffff"` even though the screen background is `#f8fafc`, to guarantee scan contrast).
- **Scan-or-manual parity (D-09):** every scan screen shows BOTH the camera-trigger button and a manual-entry text-link in the same footer area, mirroring `QRScannerScreen.js`'s existing footer button stack (`gap: 16`) — add the manual-entry link there, do not hide it behind a secondary menu.
