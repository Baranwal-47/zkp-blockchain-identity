<objective>
Build the governed erasure endpoint: `POST /api/erasure/initiate` destroys 2 of the 3 Shamir shares (custodyShareB + custodyShareC) for a student's credential via an atomic, irreversible MongoDB `$unset`, flags the record `erased`, and best-effort unpins the ciphertext + DEK envelope from IPFS without ever rolling back the destruction on an unpin failure.

Purpose: ERASE-01 (destroy ≥2 shares so recovery permanently fails) and ERASE-02 (best-effort IPFS cleanup + erased flag; on-chain `revoked` remains the authoritative proof-rejection signal, independent of this storage-layer best-effort).
Output: erasureService.js (destroyShares + bestEffortUnpin), erasureController.js, erasureRoutes.js, app.js mount, erasure.smoke.mjs proving post-erasure reconstruction failure, plus the Dashboard's destructive "Erase" action and "Erased" status badge — erasure is the most demo-critical irreversible action in this phase and needs a visible, deliberately scary confirmation, not a curl command.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → /api/erasure/initiate | Bearer JWT crosses here; only AcadAdmin role may trigger irreversible destruction |
| MongoDB $unset write → Pinata unpin call | destruction must commit before any best-effort cleanup attempt; cleanup failure must never roll back destruction |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-13 | Elevation of Privilege | Non-AcadAdmin triggers erasure | mitigate | initiateErasure enforces `req.user.role === "acadadmin"`, else 403 (mirrors 11-01 recovery initiate gate) |
| T-11-14 | Spoofing | POST /erasure/initiate unauthenticated | mitigate | `router.use(requireAuth)` rejects no/invalid Bearer with 401 before destroyShares runs |
| T-11-15 | Repudiation | Erasure happens with no durable record | mitigate | `erased:true` + `erasedAt` persisted on the Student doc; this is the audit trail (custodyShareA is deliberately kept, visible but useless alone) |
| T-11-16 | Tampering | Re-erasure of an already-erased record | mitigate | destroyShares throws 409 if `student.erased` is already true |
| T-11-17 | Denial of Service | IPFS unpin failure blocks/rolls back share destruction | mitigate | destroyShares commits via `findByIdAndUpdate` BEFORE bestEffortUnpin is ever called; bestEffortUnpin never throws (try/catch swallows all errors, logs + returns reason) |
| T-11-18 | Information Disclosure | Destroyed share values retained in a log/audit copy | mitigate | No console.log of share content anywhere in erasureService.js; the only place custodyShareB/C values are referenced is the `$unset` operator itself, which removes them |
| T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages this plan (axios already a dependency); nothing to audit |
</threat_model>
