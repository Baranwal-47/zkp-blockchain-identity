<objective>
Wire the two recovery operations into the session-completion path defined by plan 11-01. Case B (device-loss) re-wraps the reconstructed DEK to the student's new on-device pubkey and re-pins the DEK envelope. Case A (credential-modification) decrypts the existing credential, applies attribute updates against the frozen 7-attribute set, recomputes the Merkle root, re-encrypts with the SAME DEK, re-pins, and re-anchors on-chain via the same direct issuer-EOA write createStudent/updateStudent already use (`anchorCredentialOnChain`) — `issueCredential` is `onlyIssuer`, not Safe-governed, so failure only sets `anchorPending`/`lastAnchorError` as a retry signal (Q3, corrected).

Purpose: REC-02 (device-loss restores daily access on the new key) and REC-03 (credential modification preserves the frozen field set so proofs still verify).
Output: `reissueWithDEK(studentId, attributeUpdates, dek)` in studentService.js (the Phase-11 hand-off `updateStudent()` deliberately deferred), Case A/Case B operation functions in recoveryService.js dispatched from submitShare, recovery-ops.smoke.mjs, and the RecoveryPage UI polish that turns the raw API response into a plain-language outcome plus a one-click "Recover" entry point from the Dashboard. Ends with a human-verify checkpoint for the live end-to-end browser flow (no curl).

Case A's on-chain step is a direct issuer-EOA re-anchor (`anchorCredentialOnChain`), not a Safe proposal — `CredentialRegistry.issueCredential` is `onlyIssuer`; only `revokeCredential` is `onlyAdmin`/Safe-governed. This mirrors `createStudent`'s existing try/catch anchor pattern exactly (see 11-RESEARCH.md Q3 resolution).
</objective>
