## Spacing Scale

Declared values (must be multiples of 4), extracted from `LoginScreen.js` / `StudentProfileScreen.js`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, tight margins (e.g. `cardTitle` marginBottom) |
| sm | 8px | Compact spacing (label marginBottom, dot gaps) |
| md | 16px | Default card padding, section marginBottom |
| lg | 20-24px | Screen padding (`scrollContent.padding: 24`), card padding |
| xl | 32-36px | Header block marginBottom (36px on LoginScreen) |
| 2xl | 48px | not used yet in existing screens — reserve for major breaks if needed |

Exceptions: existing screens use 14px (input padding), 18px (generate button paddingVertical) — non-4-multiples already present in codebase precedent. `ClaimCredentialScreen` should stay on the 4/8/16/20/24 scale where new values are introduced; do not block on matching legacy 14/18px exactly if reusing literal button/input styles via copy-paste from `LoginScreen.js`.

## Color

Extracted from existing screens (`#f8fafc` background, `#3b82f6` primary blue, `#1e293b` dark text) — this is the established indigo/neutral palette referenced in CLAUDE.md ("light modern indigo/neutral theme, IIITDM maroon as optional accent"). No maroon accent is introduced in this phase — claim flow is a transactional/security screen, not a branding surface.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8fafc` | Screen background (`container.backgroundColor`) |
| Secondary (30%) | `#ffffff` | Card surfaces (form/status card with shadow, `borderRadius: 16`) |
| Accent (10%) | `#3b82f6` | Primary CTA button background, retry button, ActivityIndicator tint, selected/active state border |
| Destructive | `#ef4444` | Error text/icon only — claim failure message; no destructive *action* exists in this phase (no delete/revoke UI), so this is informational-error color only, not a confirm-destroy button |

Accent (`#3b82f6`) reserved for: the "Try again" retry button, the loading `ActivityIndicator` color, and (if a manual entry point is ever shown) any primary CTA. Do **not** use accent on body text, icons, or decorative elements — matches `LoginScreen.js` `loginButton`/`loginButtonText` usage exactly.

Status-state colors (new for this phase, derived from existing semantic colors already in `StudentProfileScreen.js`):

| State | Color | Source |

## Copywriting Contract

`ClaimCredentialScreen` is a fully silent auto-triggered flow (CONTEXT.md D-01) — no confirmation tap, no destructive actions. Copy must clearly communicate: this is a one-time, automatic, on-device security setup the student cannot skip or misconfigure.

| Element | Copy |
|---------|------|
| Screen title (header) | "Setting Up Your Credential" |
| Loading state heading | "Securing your credential…" |
| Loading state body | "Generating your private key on this device. This stays on your phone and is never sent anywhere." |
| Server-wait sub-state (after pubkey POST succeeds, while backend wraps DEK) | "Almost done — finalizing your credential…" |
| Success transition copy | (auto-navigates to `StudentProfile` on `enrollmentPhase: "active"` — no separate success screen per D-01 silent flow; no copy needed beyond the implicit navigation) |
| Primary CTA (retry only — no primary action on success path) | "Try Again" |
| Empty state | not applicable — this screen has no data list; it is a single-purpose action screen with no empty-data state |
| Error state heading | "Couldn't Complete Setup" |
| Error state body | "Something went wrong while securing your credential. Check your connection and try again." |
| Destructive confirmation | not applicable — this phase has no destructive action. Claim failures are retryable and non-destructive (CONTEXT.md D-03: nothing server-side changes until POST succeeds, so no confirm-before-destroy dialog is needed) |

Tone: matches existing screens — short, reassuring, plain language, no jargon ("ECIES", "DEK", "secp256k1" must never appear in user-facing copy). Existing precedent: `LoginScreen.js` infoBox uses "Your institution admin adds your details..." — same register.

## Screen-Specific Interaction Contract

(Supplementary to template — captures `ClaimCredentialScreen`'s state machine per CONTEXT.md decisions, for executor reference.)

| State | Trigger | Visual | Navigation |
|-------|---------|--------|------------|
| `generating-keys` | Screen mount (auto, no tap) | Centered `ActivityIndicator` (color `#3b82f6`) + "Securing your credential…" heading + reassurance body copy, on white card over `#f8fafc` bg | none |
| `submitting-pubkey` | Keygen + SecureStore write succeed | Same loading card, body copy updates to "Almost done — finalizing your credential…" | none |
| `success` | `POST /students/:id/pubkey` returns `enrollmentPhase: "active"` | No distinct success screen — immediate auto-navigate | `navigation.navigate('StudentProfile', { student })`, mirrors `LoginScreen.js` `handleLogin` pattern |
| `error` | Keygen throws OR POST fails (network/409/400) | Red-tinted icon or heading ("Couldn't Complete Setup"), error body, single `Try Again` button (`#3b82f6` bg, white text — matches `loginButton` style) | stays on `ClaimCredentialScreen`; tapping retry re-runs only the POST step (not keygen) per D-02 |

Layout structure: reuse `LoginScreen.js` container pattern — `KeyboardAvoidingView` not needed (no text input on this screen), use plain `View` with `flex: 1, backgroundColor: '#f8fafc'`, centered content card (`backgroundColor: '#ffffff', borderRadius: 16, padding: 24`, same shadow recipe: `shadowColor: '#000', shadowOffset: {width:0,height:2}, shadowOpacity: 0.07, shadowRadius: 8, elevation: 3`).

Header: register in `App.js` Stack with `defaultHeaderStyle` (blue `#3b82f6` header, white title text), `title: 'Claim Your Credential'`, `headerLeft: null` and `gestureEnabled: false` (matches `LoadingScreen` precedent — prevents back-swipe mid-claim, since this is a mandatory one-time gate per D-01/D-06).
