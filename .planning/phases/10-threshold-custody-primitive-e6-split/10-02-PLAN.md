<objective>
Wire the Wave-1 primitives into the live issuance and claim flow, and remove the single-custody `student.dek` field. At `createStudent` / `insertBulkStudents`, split the DEK 2-of-3 and store Share A plaintext + Shares B/C RSA-wrapped to the Registrar/Dean public keys (CUST-02, D-02, D-03, D-04, D-05). Remove the schema `dek` field and rewire `claimCredential` so the only transient plaintext DEK lives in a clearly-relabeled `pendingDek` field that is wiped at claim — the Shamir shares become the sole custodial recovery copy (CUST-03, D-06, D-07).

Purpose: This is the plan that actually closes v2.0's documented single-custody interim gap. After it, inspecting the admin DB/process alone never yields 2 usable shares.
Output: modified `Student.js`, `studentService.js`; new `services/custodianKeys.js` lazy loader; an ad-hoc issuance smoke script.

**OPEN QUESTION #1 — RESOLVED BY USER (flagged here so the executor does NOT conflate fields):**
The custodial recovery copy of the DEK is the **Shamir 2-of-3 split (3 shares)**, written at issuance. A **transient plaintext DEK MAY persist in Mongo between issuance and claim** so it can be ECIES-wrapped to the student's pubkey at claim — but it MUST live in a clearly-relabeled NON-`dek` field named `pendingDek`, and MUST be deleted (`$unset`) at claim, exactly the same lifecycle window as today's `student.dek`. This satisfies CUST-03 because CUST-03's "no plaintext DEK as a substitute for real custody" refers to the *custodial recovery copy* — which is now the shares, NOT this transient claim-window artifact. Do NOT plan or implement custodian-threshold participation at claim time (that is Phase 11). The Shamir split happens at issuance; the wrap happens at claim using `pendingDek`; `pendingDek` is then wiped.

**UPDATE-PATH DEFERRAL (resolves the open-ended "retarget or remove" — see Task 2):**
`updateStudent` (PUT /api/students/:id) today re-encrypts/re-issues on attribute edits by reusing the plaintext `student.dek`. After this phase, an already-claimed/active student has NO plaintext DEK on the backend (pendingDek was `$unset` at claim; only the 3 shares + the ECIES envelope remain). Re-issuing for such a student requires reconstructing the DEK from a 2-of-3 custodian Shamir session — which is **Phase 11** (Case A modification). For this phase, the re-issuance branch MUST fail loudly with an explicit Phase-11 error for any student with no `pendingDek`, and MUST NOT reuse, retarget, or fabricate any plaintext DEK. (A student still in the issuance→claim window — i.e. still holding `pendingDek` — MAY re-issue from `pendingDek` if that path already exists; the loud-failure requirement is specifically for the already-claimed/no-`pendingDek` case.) Do NOT pull Phase 11 reconstruction into this phase.
</objective>
