<objective>
Build the one-time custodian onboarding surface and dev-keygen tooling Phase 10's hybrid custody split depends on (D-10, CUST-02 setup work). Three deliverables: (1) a backend `POST /api/custodians/register-key` endpoint — requireAuth-gated, role-ownership-enforced — that accepts a custodian's RSA-2048 PUBLIC key PEM, validates format + modulus length, and stores ONLY the public key to that role's configured `.pem` path (the same path `custodianKeys.js` reads in Plan 02); (2) a minimal admin-frontend onboarding page that generates the RSA-2048 keypair CLIENT-SIDE via WebCrypto, saves the PRIVATE key to the official's own device, and POSTs ONLY the public key; (3) a dev keygen helper script that provisions throwaway RSA-2048 public PEMs to the configured paths so local issuance (Plan 02's real Mongo-connected flow) has custodian public keys without the browser flow.

Purpose: D-10 is the single most important control in this phase — the custodian private key is born in the official's browser and never transmitted, so "the admin server never holds a private custodian key" is cryptographically true, not asserted. This plan delivers the registration + onboarding + dev-provisioning that make the Plan 02 split runnable end-to-end.
Output: `scripts/generateCustodianKeys.js`; `services/custodianService.js`; `controllers/custodianController.js`; `routes/custodianRoutes.js` mounted in `app.js`; new env vars in `.env.example`; `CustodianOnboardingPage.jsx` routed in `App.jsx`; a registration smoke script.

This plan is **wave 1, depends_on []** — it imports neither the Plan 01 crypto primitives nor the Plan 02 service changes; it is independent and runs in parallel with Plan 01. It is sequenced BEFORE the phase-gate device checkpoint so the dev keygen script can write `registrar_public.pem`/`dean_public.pem` to the configured paths, making Plan 02's real Mongo-connected issuance exercisable. (Plan 02's own `issuance-custody.smoke.mjs` uses in-memory throwaway keypairs and does not block on this plan.)
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| official's browser → backend | The RSA-2048 keypair is generated in the official's browser; ONLY the public key crosses this boundary — the private key never leaves the device |
| client → POST /api/custodians/register-key | Untrusted PEM + role input crosses here; validated (format, modulus 2048, public-only) and role-ownership-checked before any write |
| controller → filesystem (.pem path) | The validated public PEM is written to the role's configured path that Plan 02's custodianKeys.js reads; no private key is ever written by the endpoint |
