<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deployer EOA → registry contract | Deployer holds admin until handoff; a wrong target in transferAdmin could strand admin |
| pendingAdmin (Safe) → registry contract | Only the Safe can complete the handoff via acceptAdmin |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering / DoS | transferAdmin to a wrong/typo'd or malicious address bricking the registry | mitigate | 2-step transfer: `acceptAdmin()` requires the new admin to actively claim it (`msg.sender == pendingAdmin`); a typo'd address that never calls acceptAdmin leaves the existing admin in place and re-transferable. Task 2 test asserts non-pendingAdmin acceptAdmin reverts. |
| T-09-02 | Elevation of Privilege | non-admin calling transferAdmin to seize the registry | mitigate | `transferAdmin` is `onlyAdmin`-gated; Task 2 test asserts a stranger call reverts with "Not authorized". |
| T-09-03 | Elevation of Privilege | old admin still mutating registry after intended handoff | mitigate | `acceptAdmin` atomically reassigns `admin` and zeroes `pendingAdmin`; Task 2 test asserts old admin's issueCredential reverts post-handoff. |
| T-09-04 | Tampering | accidental edit to frozen issueCredential/revokeCredential or the verifier | accept (process control) | Acceptance criteria require `git diff` to show only additions; circuit/verifier files are out of `files_modified` scope entirely. |
</threat_model>
