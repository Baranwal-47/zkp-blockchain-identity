## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api/admin/role-login | Untrusted password input; lightweight env compare |
| browser -> /api/safe/* | Untrusted safeTxHash/signature input crossing into Safe Tx Service |
| role-login JWT -> /api/safe authorization | JWT gates UI access but not signing capability |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-09 | Spoofing | role-login password brute-force / compromise reaching Pending Approvals | mitigate (layered) | Compromising the lightweight password grants UI visibility only — it cannot produce a Safe signature without the corresponding MetaMask private key (D-01). Accepted interim auth posture per D-09/HARD-01 (no bcrypt this phase). |
| T-09-10 | Tampering | malformed/injected safeTxHash or signature reaching api-kit | mitigate | joi/regex validation of safeTxHash (0x + 64 hex) and signerAddress (0x + 40 hex) at the route boundary before any safeService call (RESEARCH V5). |
| T-09-11 | Elevation of Privilege | execute auto-firing the instant threshold is met (violates D-06) | mitigate | Execute is its own POST /execute route; signPendingTx never calls executeTransaction. Acceptance criteria assert separation. |
| T-09-12 | Spoofing | unauthenticated access to /api/safe pending/sign/execute | mitigate | /api/safe requires the role-login JWT via the existing auth-guard middleware reused from /api/admin or /api/students. |
| T-09-13 | Information Disclosure | committing real passwords/keys to .env.example | mitigate | Task 3 uses placeholders only; acceptance criteria forbid real 64-hex keys in the example file. |
</threat_model>
