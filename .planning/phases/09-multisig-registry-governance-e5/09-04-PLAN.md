<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser localStorage (officialToken vs adminToken) | Two distinct auth tokens must not collide |
| MetaMask connected account -> expected Safe owner | Client must verify the right account is connected before signing |
| frontend -> /api/safe/* | UI relays signatures; backend re-validates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-14 | Spoofing / Tampering | officialToken and adminToken overwriting each other, granting wrong-scope access or breaking admin auth | mitigate | api.js interceptor branches by config.url and stores tokens under distinct keys; acceptance criteria assert both keys are referenced and RoleLoginPage never writes adminToken. |
| T-09-15 | Spoofing | official signs with the wrong MetaMask account (e.g., deployer EOA), producing a confusing "Sender is not an owner" error | mitigate | After eth_requestAccounts, compare connected address (case-insensitive) to the role's expected owner; block signing + show the destructive mismatch banner before any /safe/sign call (RESEARCH Pitfall 4). |
| T-09-16 | Elevation of Privilege | Execute auto-firing on the 2nd signature (violates D-06) | mitigate | Execute disabled until signedCount >= threshold, then still requires a window.confirm; onSign never triggers execute. Acceptance criteria assert separation. |
| T-09-17 | Spoofing | password-only role login mistaken for real signing authority | accept | Layered: role login grants UI visibility only; signing requires the MetaMask owner key (D-01). Interim posture per D-09/HARD-01. |
</threat_model>
