## Integration & E2E Findings (via gsd-integration-checker)

**Wired correctly (13 of 15 checked links):**
- Field-set consistency: `identityCommitment.js` (Phase 1) and `zkp-backend/lib/encoding.js` (Phase 4) are algorithmically identical — no chunk-count, field-order, or hash drift.
- Circuit artifacts: `identity.wasm`/`identity_final.zkey`/`verification_key.json` are byte-identical between `zk-proofs/build/` and `zkp-backend/` (Phase 3 -> Phase 4).
- Public signal order/count: `server.js` correctly indexes the 19-signal layout defined in `build/identity.sym`.
- Verifier address: `VERIFIER_ADDRESS` env var matches the real Sepolia deploy; stale hardcoded fallbacks confirmed absent.
- The previously-flagged Phase-3-review issue (`server.js` still using the old 5-field shape, noted in `03-REVIEW.md` WR-01) is confirmed fully resolved by Phase 4's rewrite.

**Broken (2 findings, both affecting the only real non-test client):**
1. **`digital-app/screens/LoadingScreen.js`** still POSTs the pre-rebuild flat 5-field body (`name, rollNo, dob, phoneNo, branch`) to `/generate-proof`. The rebuilt endpoint requires the new `attrs` object shape and will return HTTP 400. Affects **BACK-01**.
2. Neither `LoadingScreen.js` nor `VerifyProof.js` ever calls `POST /session/nonce` before `/generate-proof`/`/verify`, so the nonce lifecycle (**REPL-03**) is unreachable from the app's current code, even though it is fully correct and tested server-side.

Planning docs (`05-CONTEXT.md`) explicitly scoped `digital-app/screens/ShowProof.js` as known-stale and out of scope for this milestone, but did not identify that `LoadingScreen.js` and `VerifyProof.js` — the actual proof-generation/verification entry points — carry the identical staleness. This was not caught by any phase's own verification because all 5 phases verified backend/circuit code in isolation (via tests and `bench.js`), and none of them exercised the mobile client against the rebuilt API.
